# Menu — Routes list access, tracks/routes separation and pinned-route normalisation

**Status:** in design · nothing implemented
**Planned branch:** `feature/list-tracks-routes` (the `#new list-tracks-routes` invocation) — the branch is cut from `origin/develop` with `--no-track` before any edit; Architect cannot run it, so it is the first action in a shell-capable mode
**Feature:** Ui_Menu (the menu door and the list surface); the list split also touches Tracks, the per-kind filters touch Ui_Settings, and the route appearance stays Route's
**Review:** the 2026-10-05 review of this plan found six gaps; S4, S5, S6, S8, S11, S12, S13, S14 and S15 below carry their fixes, and D9 and D10 record the two calls they needed.
**Revision:** 2026-10-05 (later) — the user's change of mind moved the Routes row out of the ROUTING card into its own ROUTES section so the filter icons get a section header (D11, superseding D1); S8 carries the change and the drawer target is redrawn.
**Revision:** 2026-10-05 (later still) — the Routing tab's route appearance becomes a collapsible and the two route gates move to a "Route Speed and Direction" collapsible below it, while the Layers tab's direction expander is renamed to cover both kinds and noted as applying to routes too (D13, D14; S16).
**Revision:** 2026-10-05 (later again) — the user's correction moved both route collapsibles out of the Routing tab into the Layers tab, below the export/import row, under a section renamed Tracks and Routes (D15, superseding D13's placement; S17).
**Revision:** 2026-10-05 (last) — inside the Tracks and Routes card the two route collapsibles were the third section; they merge into the first, with the export/import row becoming the card's last section, and every part gains a description (D16; S18).

## Request

- Add a **Route list access** in the menu, mirroring the Tracks row, so the two lists are **functionally separated**.
- The drawer already opens one combined list; after this change a Tracks list holds recorded tracks only and a Routes list holds saved routes only.
- **Normalise route pinned handling** to match tracks: pinned is handled by the same logic tracks use — so a route pinned/not-pinned filter, and the route rendering settings, including pinned-route transparency and colours, moved out of the track appearance settings into the routes settings.

- The overlay already branches per kind: the accent map writes the pinned and history ramps for recorded tracks then the route pair for routes ([`TrackHistoryOverlay.kt:201`](../../app/src/main/java/ykws/android/maro/ui/map/TrackHistoryOverlay.kt:201), [`TrackHistoryOverlay.kt:246`](../../app/src/main/java/ykws/android/maro/ui/map/TrackHistoryOverlay.kt:246)); the card splits route stats, the Follow door and the recording guard ([`TrackHistoryOverlay.kt:558`](../../app/src/main/java/ykws/android/maro/ui/map/TrackHistoryOverlay.kt:558), [`TrackHistoryOverlay.kt:606`](../../app/src/main/java/ykws/android/maro/ui/map/TrackHistoryOverlay.kt:606)); and the Merge action refuses a route selection ([`TrackHistoryOverlay.kt:342`](../../app/src/main/java/ykws/android/maro/ui/map/TrackHistoryOverlay.kt:342)).

### The shared filter pair (the gap raised in review)

- Both kinds share one filter pair: [`trackListFilter`](../../app/src/main/java/ykws/android/maro/data/settings/SettingsManager.kt:422) drives the list, [`trackMapFilter`](../../app/src/main/java/ykws/android/maro/data/settings/SettingsManager.kt:426) drives the map render and the menu counts, linked by [`trackFilterLinked`](../../app/src/main/java/ykws/android/maro/data/settings/SettingsManager.kt:430); keys, load and save sit beside them ([`SettingsManager.kt:750`](../../app/src/main/java/ykws/android/maro/data/settings/SettingsManager.kt:750), [`SettingsManager.kt:911`](../../app/src/main/java/ykws/android/maro/data/settings/SettingsManager.kt:911)).
- The axes are `dateRange`, `pinned`, `position` and the **Kind** axis `route` (ALL · TRACKS · ROUTES) ([`ListFilter.kt:149`](../../app/src/main/java/ykws/android/maro/data/model/ListFilter.kt:149)); `matchesFilter` reads the Kind axis ([`ListFilter.kt:87`](../../app/src/main/java/ykws/android/maro/data/model/ListFilter.kt:87)).
- The map render splits membership then bounds each half — `recorded`, `routes` and the uncapped `pinned` escape — from one entry point, and **all three read the one `filter` argument** ([`MapTrackOverlayEffects.kt:503`](../../app/src/main/java/ykws/android/maro/ui/map/MapTrackOverlayEffects.kt:503), [`MapTrackOverlayEffects.kt:531`](../../app/src/main/java/ykws/android/maro/ui/map/MapTrackOverlayEffects.kt:531)).
- The counted sets exclude pinned before their cap, so a pinned item is drawn on the pinned path alone and never twice ([`MapSelectionPolicy.kt:49`](../../app/src/main/java/ykws/android/maro/data/model/MapSelectionPolicy.kt:49)) — the plan's pinned claim rests on this line.
- Consequence: with one filter pair, a Tracks filter keeps moving routes on the map and in the count, so the split is incomplete without per-kind filter instances.

### Pinned handling (the assessment)

- Pinned is meant to be **one rule for both kinds**, and today it is partly split. The **escape is shared**: `storedTrackSelection.pinned` takes every pinned summary the filter holds, uncapped, for both kinds ([`MapTrackOverlayEffects.kt:530`](../../app/src/main/java/ykws/android/maro/ui/map/MapTrackOverlayEffects.kt:530)).
- The **drawing is special-cased**: the pinned loop reads the summary's own flag through `isRoute` and, for a route, pushes it back to the ordinary route ladder and pair, so a pinned route looks unpinned while a pinned track takes the pinned look ([`MapTrackOverlayEffects.kt:346`](../../app/src/main/java/ykws/android/maro/ui/map/MapTrackOverlayEffects.kt:346), [`MapTrackOverlayEffects.kt:365`](../../app/src/main/java/ykws/android/maro/ui/map/MapTrackOverlayEffects.kt:365)). Removing that special case is what "the same logic" means.
- There is **no routes-reachable pinned axis** because the Kind axis is the only kind switch and both kinds share the filter; a route cannot be filtered to its pinned subset.
- Pinned tracks read `trackingTransparencyPinnedNewest`/`Oldest` and `trackingColorPinnedFrom`/`To` ([`SettingsManager.kt:391`](../../app/src/main/java/ykws/android/maro/data/settings/SettingsManager.kt:391), [`SettingsManager.kt:404`](../../app/src/main/java/ykws/android/maro/data/settings/SettingsManager.kt:404)); routes read `trackingTransparencyRouteNewest`/`Oldest` and `trackingColorRouteFrom`/`To` ([`SettingsManager.kt:398`](../../app/src/main/java/ykws/android/maro/data/settings/SettingsManager.kt:398), [`SettingsManager.kt:366`](../../app/src/main/java/ykws/android/maro/data/settings/SettingsManager.kt:366)).

## Target

Two kind-locked lists behind two drawer doors, two filters, a sort and a link flag per kind, and pinned handled by one rule for both kinds — the pin escapes the render cap, is filterable, and draws with the pinned look, with a pinned route taking its own pinned pair:

```text
Menu drawer
  ROUTING card
    the route ends  ·  the quick access  ·  the route summary (gated)
  ROUTES section                                    ← new, mirrors the TRACKS section
    SectionHeader Routes  →  Link · Filter · Reset
    Routes row            →  count + chevron → the Routes list
  TRACKS section
    SectionHeader Tracks  →  Link · Filter · Reset
    Tracks row            →  count + chevron → the Tracks list (recorded tracks only)

Routes list                     Tracks list
  saved routes only               recorded tracks only
  routeListFilter / routeListSort trackListFilter / trackListSort
  routeListState (its own)        trackListState (its own)
  Pinned axis (its own)           Pinned axis (its own)
  pinned first, then the rest     pinned first, then the rest
  pin, follow, export, delete     pin, resume, merge, export, delete

Map render
  a route  matches routeMapFilter      a track  matches trackMapFilter
  pinned (either kind)  → the one pinned path, uncapped, filter-bound per kind
    a pinned track  reads the pinned-track pair
    a pinned route  reads the pinned-route pair (new keys)

Settings — Routing tab
  SectionHeader Route                    → the pace and budget sliders alone (the Appearance section leaves)
Settings — Layers tab
  SectionHeader Tracks and Routes        ← renamed from Tracks
    Section 1
      Expander (the track rendering and direction groups, unchanged)
      Expander Route Appearance          → routes count · route ladder · pinned-route ladder · route colours · Active route
      Expander Route Speed and Direction → Speed colours on routes · Arrows on routes
    Section 2
      Export / Import row                → with its own description
```

## Decisions

- **D1 — superseded: the Routes row left the ROUTING card for a ROUTES section.** The first call on 2026-10-05 put the row inside the ROUTING card after `RouteSummaryBlock`; the user's change of mind the same day moved it into its own ROUTES section so its filter icons get a section header to live in (D11). The ROUTING card keeps its ends, its quick access and its gated summary.
- **D2 — hard separation, Kind axis retired.** Taken with the user: the Tracks list holds recorded tracks only and the Routes list holds routes only, and the Kind filter axis is removed rather than preset per entry point.
- **D3 — one shared overlay, scoped.** The two lists share `TrackHistoryOverlay` through a `scope` parameter rather than a second overlay file, so the card, the accent map and the actions keep one home. This is an invisible implementation choice and therefore the agent's.
- **D4 — per-kind filter instances.** Taken with the user after review: routes get their own list filter and sort, their own map filter and their own link flag, independent of the tracks set.
- **D5 — pinned is one rule for both kinds, and a pinned route gets its own appearance pair.** Taken with the user on 2026-10-05: pinned is handled by the same logic tracks use, so the `isRoute` special case that pushes a pinned route back to the ordinary route role is removed and every pinned item runs the pinned path, with only the values selected per kind. A pinned route reads its own pinned transparency and colours, held under the route settings (S9, S10).
- **D6 — the Active route line colour moves with the route rows.** Taken with the user on 2026-10-05: it is the followed route's own line colour, so it leaves the Layers tab's Tracks card with the other route rows and lands in the Routing tab (S12).
- **D7 — `showRouteHistory` as a second flag rather than a nullable `ListScope` in the chrome.** Holds the diff to the existing flag pattern and the five gate sites; a single nullable scope is the cleaner refactor and is reversible. S4 adds the mutual-exclusion guard the two-flag shape needs.
- **D8 — the pinned-route appearance is property-backed and settings-editable.** Taken with the user on 2026-10-05: the pinned-route transparency and colours are seeded from a `maro.properties` value read through the same `BuildConfig`/`AppConfig` path as the other pairs, and the values are edited in the Routing tab's Appearance block beside the moved route rows. The seed is chosen so a pinned route reads apart from a pinned track's amber.
- **D9 — Export all tracks stays the recorded tracks.** Judgement call from the review: the Settings control keeps its name and exports recorded tracks only, and routes export from the Routes list's own multi-select, so neither control silently changes what it writes. Reversible if the export is meant to cover both.
- **D10 — the shared axes stay as they are.** The `position` axis is kept on both lists for parity even though a saved route is on water by construction, so the routes list carries the same three axes as the tracks list minus the retired Kind; a route-only axis set would be a separate change.
- **D11 — a dedicated ROUTES section mirrors TRACKS.** Taken with the user on 2026-10-05 after the change of mind: the drawer's Routes row and its Link, Filter and Reset icons live in a `SectionHeader("Routes")` plus card pair mirroring the TRACKS section ([`MenuDrawerOverlay.kt:199`](../../app/src/main/java/ykws/android/maro/ui/map/MenuDrawerOverlay.kt:199)), so the map-referential filter icons have the same home as the tracks', and the ROUTING card stops carrying a list row. Supersedes D1's placement.
- **D12 — a route is always dashed.** Taken with the user on 2026-10-05, closing F3: the dashed rhythm is a route's identity, so a pinned route keeps its dash even though it now draws with the pinned pair and width.
