## Data Model

### Sealed Geometry Hierarchy
**Decision:** `MarkerGeometry` sealed class with three variants: `Pin(position)`, `Circle(center, radiusM)`, `Corridor(p1, p2, widthM)`.
**Rationale:** Exhaustive `when` matching, no default branch, compiler-enforced completeness.
**Source:** [`UserMarker.kt`](app/src/main/java/ykws/android/maro/data/model/markers/UserMarker.kt)

### Proximity Override Per Marker
**Decision:** `proximityOverrideM: Double?` on UserMarker. Always set by creation wizard with formula defaults (Pin→200m, Circle→radius×3, Corridor→width×3). Matching engine reads stored value directly — no formula defaults in matching logic. Null fallback (`?: Double.MAX_VALUE`) for legacy data.
**Rationale:** User-configurable per-marker proximity zone. Formula defaults belong in creation wizard only, not in matching engine.
**Source:** [`UserMarker.kt`](app/src/main/java/ykws/android/maro/data/model/markers/UserMarker.kt:29), [`MarkersViewModel.kt:510-515`](app/src/main/java/ykws/android/maro/ui/map/MarkersViewModel.kt:510), [`MarkerMatcher.kt:467`](app/src/main/java/ykws/android/maro/spatial/MarkerMatcher.kt:467)

### BBox Pre-Filter — REMOVED (2026-06-30)
**Decision:** REMOVED. BBox pre-filter was a performance optimization that dropped markers whose axis-aligned bounding box didn't overlap the boat's 1km search circle. **Removed per 2-gate simplification rule** — the only valid gates are zone membership and direct line-of-sight. BBox is neither.
**Source:** [`MarkerMatcher.kt`](app/src/main/java/ykws/android/maro/spatial/MarkerMatcher.kt)

### Icon → Auto-Pinned — SUPERSEDED (2026-09-04)
**Decision:** `icon != null` implies `pinned = true`. Legacy `pinned=true` without icon gets default red 📍.
**Rationale:** Single source of truth — icon presence drives pin state, not a separate boolean.
**Superseded:** see *Icon and pin decoupled* below — the icon carries no pin semantics and `pinned` is its own persisted field.

## Match Resolution

### On-Demand Only
**Decision:** No continuous 1Hz pipeline. Match triggered by boat marker tap (CenterMarkerOverlay clickable).
**Rationale:** User-triggered, <500ms acceptable. No real-time performance constraint.
**Source:** [`MarkersViewModel.kt:654-670`](app/src/main/java/ykws/android/maro/ui/map/MarkersViewModel.kt:654)

### Two-Gate Model (2026-07-01)

**Decision:** `whereAmI()` resolution uses a zone check + optional proximity pre-filter + line-of-sight.

| Step | Rule | Applies To |
|------|------|------------|
| **Zone** | Boat inside geometry → `ZoneMatch` (no LOS test) | Circle, Corridor |
| **Pre-filter** | `minBoundaryDist > proximityOverrideM` → skip (optimization, no segments tested) | Circle, Corridor |
| **Line-of-Sight** | Clear sea path to any boundary point → `LineOfSightMatch`. No distance cap. | Circle, Corridor |
| **Proximity gate** | `directDist ≤ proximityOverrideM` → `LineOfSightMatch`. No land check. | Pin only |

- **Pin markers:** Proximity gate only. No land check — a Pin behind an island still matches.
- **Circle/Corridor:** Pre-filter gates on `proximityOverrideM` (stored value, no formula defaults). Once passed, line-of-sight is the sole pass/fail criterion — no distance cap.
- **No proximity gate for circles/corridors:** Removed. The old gate rejected valid LOS matches because the unblocked boundary point was beyond an arbitrary distance threshold.
- **All matches are returned** — containment tree with `depthFirstLeavesFirst` traversal is display ordering only.

**Rationale:** The old "proximity gate" (step 7) rejected matches where the closest unblocked boundary point happened to be beyond `proximityOverrideM` — even though line-of-sight existed. This was a false negative. The pre-filter remains as a CPU optimization (don't test obviously distant markers), but once a marker passes the pre-filter, LOS alone determines the match.

**Source:** [`MarkerMatcher.kt`](app/src/main/java/ykws/android/maro/spatial/MarkerMatcher.kt)

### WhereAmIMatch Sealed Class
**Decision:** Two variants: `ZoneMatch` (boat inside geometry, purely geometric) and `LineOfSightMatch` (boat outside, sea-path distance to closest unblocked boundary point). Renamed from `ProximityMatch` (2026-07-01) — "proximity" implied a distance cap that no longer exists.
**Rationale:** Zone match skips land check. LineOfSight requires clear sea path.
**Source:** [`MarkerMatcher.kt`](app/src/main/java/ykws/android/maro/spatial/MarkerMatcher.kt)

### Display Ordering
**Decision:** Results sorted by `sortScore()` (composite: categoryBase + typeWeight × percentage), then `zoneSizeOf()` as tiebreaker, then `depthFirstLeavesFirst` traversal of the containment tree (children before parent). No MAX_RESULTS cap — all matches returned.
**Rationale:** "Smallest/most specific first" ordering. Containment tree with `depthFirstLeavesFirst` is preserved for display ordering — not a match gate.
**Source:** [`MarkerMatcher.kt`](app/src/main/java/ykws/android/maro/spatial/MarkerMatcher.kt)

### 1km Search Fence — REMOVED (2026-06-30)
**Decision:** REMOVED. The 1km BBox search fence was an arbitrary gate that dropped markers outside a 1km radius regardless of their actual proximity range. **Removed per 2-gate rule** — if a marker has a proximity range of 2km and the boat is 1.5km away with clear LOS, it should match.
**Source:** [`MarkerMatcher.kt`](app/src/main/java/ykws/android/maro/spatial/MarkerMatcher.kt)

## Land-Blocking Engine

### Boundary Point Sampling
**Decision:** `sampleBoundaryPoints()` generates points directly on geometry boundary via `pointAlongBearing` from the zone center — never via ray-intersection from the boat. Direct-line fast path: `closestGeometricBoundaryPoint()` tested first; if clear LOS, return immediately.
- **Circle:** 16 points on visible arc from center (`90°−asin(r/d)` half-arc). Tangents guaranteed at samples 0/15.
- **Corridor:** 16 points per end-cap (full 360° from center, 22.5° spacing) + 5 per edge line.
**Rationale:** `circlePointAtBearing` (ray-intersection from boat) dropped tangent samples due to planar floating-point `disc < 0`. Center-based generation via `pointAlongBearing` always succeeds.
**Source:** [`MarkerMatcher.kt`](app/src/main/java/ykws/android/maro/spatial/MarkerMatcher.kt:355)

### CoastlineSpatialIndex Integration
**Decision:** Reuse existing `CoastlineSpatialIndex` (500m grid cells). `segmentIntersectsLand(a, b): Boolean` short-circuits on first non-grazing land hit with 10m grazing tolerance.
**Rationale:** No second index build. Grid-pre-filtered segment queries.
**Source:** [`CoastlineSpatialIndex.kt`](app/src/main/java/ykws/android/maro/spatial/CoastlineSpatialIndex.kt:504)

### CoastlineSpatialIndex Integration

**Decision:** Pin → `Marker` with filled-circle `BitmapDrawable`. Circle → `Polygon` fill + `Polyline` outline + center `Marker`. Corridor → `Polygon` fill + two parallel `Polyline`s + centerline `Polyline` (50% alpha) + semi-circle caps + p1/p2 `Marker`s.

### Semi-Circle Corridor Caps
**Decision:** `addSemiCircleCaps()` draws 18-point arc polylines at p1 and p2, connecting the left and right parallel edges into a pill/racetrack shape. Fill polygon also traces the pill outline.
**Rationale:** Open parallel lines looked incomplete. Caps close the corridor band visually.

## Routing Weight

### A marker as a routing weight alone — `routingOnly` (2026-10-11)
**Decision:** `UserMarker.routingOnly: Boolean = false` (additive, no migration) marks a marker that exists only for its routing weight. One pure predicate, `MarkerMatcher.countsForWhereAmI`, excludes such a marker from `resolveAllMarkers` before any match resolves, so every consumer is spared it, and `routeEndName`'s flagged-selection fallback is guarded so a routing-only end keeps its fixed or dated name.
**Rationale:** A cost the route engine reads need not also name a place; one exclusion point keeps every where-am-i producer unchanged.
**Source:** [`UserMarker.kt`](app/src/main/java/ykws/android/maro/data/model/markers/UserMarker.kt), [`MarkerMatcher.kt`](app/src/main/java/ykws/android/maro/spatial/MarkerMatcher.kt)

### The routing-cost wall (2026-09-28)
**Decision:** The routing cost's bound has one home — `ROUTING_COST_MAX = 9` prices the marker, `ROUTING_COST_BLOCKED = 10` walls it — and `validRoutingCost` accepts `1..10`. A wall is a role, not a price.
**Rationale:** The guard and the slider no longer state the bound twice, and a reader that cares about crossing treats `10` apart from 1–9.
**Source:** [`UserMarker.kt`](app/src/main/java/ykws/android/maro/data/model/markers/UserMarker.kt)

## Filter Axes

### Two independent routing axes (2026-09-28)
**Decision:** `UserMarker.matchesFilter` gates routing on two axes — `routeCost` (ALL / WITH_COST / WITHOUT_COST) and `routeRole` (ALL / ROLE / NONE) — ANDed, so one marker answers a cost and no role at once.
**Rationale:** A single-select axis can never hold a cost and a role at once; two axes are ANDed and each can be cut alone. The grouped fallback was declined as narrower than the request.
**Source:** [`ListFilter.kt`](app/src/main/java/ykws/android/maro/data/model/ListFilter.kt), [`UserMarker.kt`](app/src/main/java/ykws/android/maro/data/model/markers/UserMarker.kt)

### One title over shared filter axes (2026-10-12)
**Decision:** `FilterControl` holds the title id drawn last and emits a `PopupSectionTitle` only when the axis's id differs from it, so the marker filter's three routing axes stand under one `Routing` title while each keeps its own card.
**Rationale:** Grouping needs no field on `FilterAxisSpec` — a repeated key is one group — and a future axis must not reuse a neighbour's key by accident.
**Source:** [`ListOverlayScaffold.kt`](app/src/main/java/ykws/android/maro/ui/components/ListOverlayScaffold.kt), [`ListFilter.kt`](app/src/main/java/ykws/android/maro/data/model/ListFilter.kt)

## Transfer

### A GPX waypoint with a payload pair (2026-10-11)
**Decision:** One marker exports as a `<wpt>` at its centre carrying two `<extensions>` payloads — a base64 protobuf blob of the whole marker and a CDATA JSON mirror of every field — under a marker namespace of its own; a batch is a ZIP of per-marker `.gpx` files.
**Rationale:** The blob is the lossless path and the mirror keeps the file readable by a human or a foreign tool; one shared `Json` home stops the two copies from drifting.
**Source:** [`MarkerPayload.kt`](app/src/main/java/ykws/android/maro/data/markers/MarkerPayload.kt), [`MarkerGpxExporter.kt`](app/src/main/java/ykws/android/maro/data/markers/MarkerGpxExporter.kt)

### The exported set and identity (2026-10-11)
**Decision:** The markers backup takes `origin == USER || trackId == null`; an imported marker's identity is the blob's `id`, else the mirror's, else the name (first-wins); a foreign waypoint is born a keeper Pin (`confirmed`, `keepable`, `origin == USER`), never an auto marker; a single-file match asks Duplicate / Override / Cancel while a ZIP always skips. Every write goes through `UserMarkerRepository`, whose mutex and change channel are the whole refresh.
**Rationale:** A track-less auto marker would otherwise be stranded; an import must never land where the startup cleanup deletes it; a ZIP re-import is idempotent.
**Source:** [`MarkerGpxImporter.kt`](app/src/main/java/ykws/android/maro/data/markers/MarkerGpxImporter.kt), [`MarkerSharing.kt`](app/src/main/java/ykws/android/maro/ui/map/MarkerSharing.kt)

## Focus Framing

### The fit includes the proximity collar (2026-10-11)
**Decision:** A marker's dashboard-open fit frames its body plus the proximity collar, reading the reach through its one home `markerProximityRangeM`; the pin's zoom-in-only lock is dropped and `marker.focus.pinFootprintM` becomes its floor.
**Rationale:** The proximity ring is drawn outward from the body, so framing the body alone let it spill past the screen edge; one reach home keeps the framing and the ring from disagreeing.
**Source:** [`MarkerFocus.kt`](app/src/main/java/ykws/android/maro/ui/map/MarkerFocus.kt)
