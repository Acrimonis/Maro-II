# Inspect Mode — drag-to-select on the map

> Host feature: **UI_Map** (map interaction + map chrome). The card, its Prev/Next walk and the close
> rules stay owned by **Ui_General** / **Markers**; this plan adds a new writer of the selection and a
> new `DrawerSource`.
> Decisions arbitrated on 2026-09-17, including a challenge pass and an eight-point review walk. No
> design item remains open; §8 carries the checks still owed.

## Problem

- On the water the screen is small, the boat is moving, and the visible map carries several tracks and markers, so "what is this line near me?" cannot be answered by tapping: a track stroke is a few pixels wide and a marker's tap zone a few metres, and a finger overshoots both.
- An item can today only be opened from the two lists, the menu's chevron, a tap on a marker's proximity zone, or the where-am-i query — a track has no map-tap route at all, so the question is unanswerable from the map itself.
- Inspect mode answers it: drag the map until the target is the closest thing on screen, watch the highlight follow it, and open the item without leaving the map or moving the camera.

## 1. Behaviour

- **Toggle** — a square in the map's top-left status row, between the 🌊/🏔️ and 📵 toggles, so the row reads GPS, record, earth/water, inspect, lock (+ the conditional recenter). Glyph 🕵🏽 (`U+1F575` + `U+1F3FD`, hard-coded like the row's other glyphs), active face when armed, off by default, session-lived (`rememberSaveable`), never persisted.
- **It is disabled while nothing is inspectable** — both filters empty, or both layers off — so a mode that could never pick anything cannot be armed. The gate applies only while disarmed: an armed mode always stays tappable, or a filter change could trap the user in a mode they cannot switch off.
- The sleuth reads as "what is under here" — the very question the mode answers — and wears the row's shared toggle size. Both code points are needed: the detective alone renders monochrome, so the `U+1F3FD` skin-tone modifier is what makes it an emoji.
- **Sweep** — dragging or pinching re-ranks the inspectable items by distance from the marker point; the closest item whose geometry overlaps the viewport wears the gold outline, and when the viewport holds no candidate the outline clears and the scan falls idle until the map moves again.
- **Pick** — the pick is the *opening* of the card, not the highlight: nothing extra is computed while sweeping, and the ladder's origin is snapshotted at that moment (§5).
- **Trigger** — a genuine finger lift starts the clock and the dwell runs only while the map is quiet; when it expires the highlighted item is selected **exactly as a list selection does**: the same openers, the same camera (animate to a marker, zoom to fit a track) and the same look. The pick ends the mode when its card lands, so a gesture cannot yield a second one.
- **A tap that never moved the map still commits** — the highlight is the promise and the release is the acceptance, so a lift on an unmoved map picks what is highlighted once the same quiet wait has passed. The mode never waits for a drag: the release is the whole instruction.
- **The mode is an entry point, not a second feature.** From "selected" onwards nothing is inspect-specific — the camera, the card, the walk and the rendering are the shared selection path; the only thing the mode contributes is a different walk world, the frozen ladder instead of a list.
- **Navigation is free** — with a card open the map can still be dragged and pinched, and movement never closes the card: its life is tied to Back (gesture or button) and to a change of the referential its walk reads, not to the gesture.
- **Ladder** — with a card open, Prev/Next walks the frozen distance ladder over the inspectable set, index-based so Next then Prev returns to the same item; because the ladder mixes both types, a step landing on the other type keeps the one card and swaps its content, then lets it resize to fit (§5).
- **Taps** — a tap that lands on a marker while armed opens it through the same inspect opener — the frozen ladder once one exists, and before the first pick the map-filtered collection the tap itself came from, never the list world — and that open disarms the mode exactly as a pick does.
- **Panels** — the menu, settings, the two lists and the layer fan leave the mode armed and leave an open card open; the marker wizard disarms the mode (it owns the map centre and puts the crosshair there).
- **Exit** — the mode stands down when the card its pick opened lands, but the card itself holds the centre and the capture until it closes, and that close is the mode's single exit: the capture taken at arming is applied there, once — GPS re-pins or restarts the delay-return from that moment, demo puts its captured centre back (§6). An open that lands no card leaves the mode armed and applies nothing, and a manual disarm (the toggle, the wizard) applies the capture only when no card is left standing, so a toggle with a card up lets the close restore rather than restoring twice. The canonical guard holds: a map the user moved after the card opened is left where they put it, exactly as a list-opened card leaves it. A referential change that rewrites the ladder's world (the map filter, a list reset) closes the card with it — the ladder is gone, so there is nothing left to walk, and that close is the exit.
- **Configuration changes are a non-event** — the manifest declares `configChanges`, so rotation never recreates the activity and the mode, its card and its ladder all survive.

## 2. Anchor, eligibility and the highlight

- **Anchor** = the geo point under the centre marker, i.e. the map centre including `setMapCenterOffset`. Verify in code that `mapView.mapCenter` already carries the offset; the fallback is `projection.fromPixels(centreX, centreY + offsetPx)`. The anchor is never the finger.
- **The sweep reads the raw centre, never `uiMapCenter`**, which is sampled to ~3 Hz for Compose and would lag a fast drag by up to a third of a second.
- **The visible area defines eligibility** — a candidate is eligible when its geometry overlaps the current viewport, tested by bounding box against the projection's visible bounds. There is no radius, no ring and no selection zone: the mode can only pick what the user can see, so it never declares a reach the screen does not show and never offers an item off screen.
- **Each candidate carries a bbox, derived once at warm time** — trivial for a point (its own position), computed and cached for a line (its extent, in the warm pass §3 already runs). The per-frame test is then one rectangle comparison per candidate, with no geometry walk.
- **The highlight is the closest eligible candidate to the anchor** — overlap first, distance second, so a nearer item off screen loses to a farther one on it.
- **An empty viewport clears the highlight and stops the scan** — with no candidate overlapping the viewport the gold goes and the sweep suspends its fetching entirely, resuming only when the map moves again. An empty screen is then an honest answer rather than a mode still computing about nothing.

## 3. Candidates, metric and ranking

- **One source for the sweep and the ladder: the map-filtered items whose layer is showing.** The render cap is not a restriction — a filtered track beyond it is a legitimate pick and the mode's own overlay draws it — while a hidden marker layer or hidden tracks contribute nothing, so the mode can never resurrect what the user switched off. The live recording is the only other exclusion, having no card behind it.
- **Distance is measured exactly, from points loaded once.** Arming warms those tracks into the in-memory detail cache and derives each candidate's bbox in the same pass (§2), off the UI thread, so a drag frame never reads the file and no second geometry representation exists; at 20–30 tracks of a couple of thousand stored points each, that warm-up is a few hundred milliseconds once and the resident set stays a few megabytes.
- **A simplified copy would not earn its keep at this scale**: thirty tracks at ~2k points is ~60k segment tests per sweep frame, about a third of a millisecond on a worker, so exact and simplified distances cost the same order of magnitude — which is why the plan measures exactly instead of carrying a tolerance and a budget forever.
- **The precision ceiling is upstream.** Stored tracks were already simplified at finalize by the user's own recording setting (ε = 3 m by default, `trackSimplifyEpsilonM`), so inspect is as exact as that data allows and the only way past it is the recording setting, for tracks recorded afterwards.
- **A measured escape hatch, not a first design.** If a device pass ever shows the scan hurting — a filtered set in the hundreds, or tracks in the tens of thousands of points — the fix is one retained simplified copy per track (the app's own Douglas–Peucker, [`TrackSimplifier`](app/src/main/java/ykws/android/maro/data/track/TrackSimplifier.kt:38), at a tolerance under the recording setting with a point budget) shared by the sweep and the ladder.
- **Metric — points and lines only, never areas.** A marker measures to its own point (a pin at its position, a circle at its centre) and a line to its line (a track's polyline, a corridor's centre line), segment-wise and GAP-aware, so one number compares all of them. A corridor's band width is ignored and no shape contributes inside-ness, so being *inside* a circle never yields 0 — that is what stops a zone from owning the ladder merely by containing the boat, and it is a deliberate trade rather than an oversight.
- **Ordering** — ascending distance, tie-break markers before tracks, then id ascending, so it is deterministic and testable.
- **No hysteresis: always the true closest.** The candidate is simply the closest eligible item on every re-rank, with no incumbent held for stability and no margin to overcome — the mode never resists a change the geometry has already made.
- **Quiescence** — the sweep re-ranks on every pan and zoom, and the trigger clock resets on every such event rather than only on a candidate change, because a fling moves the map with no touch and would otherwise open a card mid-flight. Arming seeds one motion of its own so the gold is live before any touch, and that seed must pick nothing: the clock starts only on a genuine finger lift (§5), so with no lift there is no tick.
- **Always publish, never starve.** Stale motion ticks are conflated and a scan in flight is never cancelled — the pipeline uses `collect`, not `collectLatest` — so every tick publishes its result and the previous highlight stands until its successor arrives. The sweep needs only the nearest eligible item, an O(N) minimum over warm geometry off the UI thread, while the ladder needs the whole order, a full sort once at the pick, and since both read the same loaded geometry the two cannot disagree.
- **Pure class** — `InspectRanking` (candidates + viewport bounds + anchor → eligible ids in rank order) holds the overlap test, the metric, the ordering and the tie-break, with no Android dependency, and carries the unit tests.

## 4. Painting

- **The mode owns one overlay and paints nothing else.** The candidate is drawn as a single extra line that the mode adds and removes itself, wearing the selection's look from the same style functions **and the same plan inputs** (`trackArrows`, `trackColours`, the eye) the canonical path uses, so the preview and the committed look are identical by construction rather than by eye — gold only where a selection would be gold, banded where it would be banded. The track's own drawing is never touched, there is no prior state to restore, and a candidate beyond the render cap and one already drawn take the same path.
- **Its title must carry a track-band prefix** (`track_hist_` or a new prefix registered in `OverlayZOrder`): `reorder()` buckets by title prefix and anything unrecognised lands in the base band, below every track, breaking the "selection drawn above every other trace" invariant.
- **A rebuild can float other tracks above it**, so a **rebuild generation counter** — bumped when the track effect finishes — re-stacks the overlay after each pass. The counter is the only new state and the re-stack is one list operation, not a repaint.
- The selection's opaque casing hides the candidate's own default stroke underneath, which is the one thing to confirm on device at the widest default width.
- **Markers are not treated this way** — their overlay rebuild is a short list, so the candidate id simply joins their existing inputs.
- **Chevrons are ignored while sweeping** — no `TrackDirectionOverlay` work during the drag; it is the expensive part of a rebuild and is not wanted mid-gesture.
- **On commit the owned overlay is dropped and the canonical rebuild paints the selection** with the same look from the same style functions, so the swap is invisible and the selection has one author once the card is open. The overlay is dropped when the mode is disarmed too — and the pick disarms it as its card lands (§5), so the stand-down needs no rule of its own.
- **The commit's rebuild must not flash**: the candidate's track is loaded by definition, so build the replacement overlays into a local list and swap them in one non-suspending `removeAll` + `addAll` + `invalidate` block. A suspension between removal and re-add would blank tracks for a frame, so warm geometry comes first and the swapping second.
- A literal double buffer (a second `MapView`, an offscreen overlay set) is not the answer: the artefact is a mid-rebuild suspension, not tearing, and two map views would double tile decoding and memory for a frame the single block already makes indivisible.

## 5. The pick: trigger, ladder, walk, openers

- **One trigger: a lift plus quiet** — the clock starts on a genuine finger lift and runs only while the map is quiet, where quiet is the whole of the user's idleness rather than the map's alone: the lift, a pan, a zoom, a lock flip, a layer chip and a settings write each restart it, and a panel suspends it outright. When it reaches `inspectDwellMs` with the highlight still current, that item is selected and its card opens. Nothing can pick without a lift, so the arming seed needs no guard of its own — its tick has no lift behind it and stops there.
- **A resting finger never picks, and the fling after a release cannot** — a finger still held keeps the clock from starting at all, and the fling keeps resetting it, so the dwell only ever completes on a map that has come to rest. The lift is the instruction and the quiet is the confirmation.
- **No re-fire for the same id** — the pick's own camera move is a pan event, so without this guard the reset clock would open the same item a second time; the committed id is held for the rest of the session. The guard is reset per armed session, so a second session may pick the item the first one picked.
- **The centre marker's tap stops meaning whereAmI while armed** — the mode owns that point, and letting the tap run its query would race the trigger for the same card slot. Taps that land on a map marker keep their route and go through the inspect opener.
- **Release detection** — osmdroid owns the gesture, and the app already owns a non-consuming observer on it (the map's existing `OnTouchListener` that feeds `notifyUserInteraction`); the mode reuses that signal rather than installing a second listener, which would replace the first and break the follow-suppression contract. That same gesture boundary is what supplies the lift: the clock may start only on an up event, so a long press, a held drag or a pinch in progress picks nothing however still the map is.
- **The ladder is one bounded pass, run at the pick**, over the inspectable candidates and the anchor **snapshotted at that moment**, so the sequence is reproducible and never re-ranks as the boat moves or the map drifts. It keeps only `(id, distance)`, measured through the same warm geometry as the sweep.
- **The pass is synchronous at this scale**: it sorts a few dozen warm entries before the card opens, so the card appears with its buttons already correct and no progressive enabling is needed; the earlier "lights up as targets land" behaviour belongs to a slower geometry model and is deliberately not implemented.
- **The inspect openers are the canonical openers.** The pick and every step call the same code a list selection calls — the same camera, the same pre-navigation capture, the same rendering — with one parameter differing: the walk world handed over is the frozen ladder instead of the list world. There is no quiet variant, so any future change to how a selection is framed or painted reaches the mode for free.
- **One clock, one key** — the wait is a debounce over a single key holding the candidate id, the activity tick, the panel state and the lift, so a new candidate, a pan, a zoom, a lift and any other thing the user did each restart the dwell with no counter of their own; nothing may be lifted out of that key set — a separate ticking effect, or a counter living outside it, would bring back a clock no candidate change can cancel. That activity is one input to the mode rather than a reset scattered through the map's call sites: the zoom buttons and every other control already surface as map motion or a panel change, and what does not — the screen-lock square, a layer chip, a settings write — bumps the same tick, which the mode folds with its own motion. The lift joins those keys as a latch rather than a counter: it is set by the lift alone and cleared per armed session, so it opens the clock where the arming seed cannot, and it can never keep a clock alive that a candidate change has cancelled. A tap that never moved the map is exactly the case the latch exists for — nothing else in the key moves, so the latch is the whole key change — and its documented trade is the mirror of it: the latch stays set for the rest of the armed session, so a wait a **later** key started (a motion, a panel close) completes on the lift the user gave earlier, which is recorded here as a trade rather than as a defect.
- **A panel suspends the clock rather than pausing it** — while the menu, settings, either list or the layer fan owns the screen the wait must not run, and the panel state is part of the key: opening one drops the wait in progress, and closing one starts a full `inspectDwellMs` rather than resuming the wait it interrupted, so nothing is picked behind a panel or in the frame the panel closes.
- **The camera move is itself a pan event**: it resets the trigger clock and re-ranks the sweep from the new centre. The mode is already standing down by the time its card lands, so the move cannot become a second pick, and the mode's own line goes with the mode — the canonical rebuild is the one author of the gold.
- **The walk is owned by one inspect cursor, not by the drawers.** The drawers each walk their own kind (a marker card steps markers, a track card steps tracks), so a merged ladder needs a cursor above them: `(id, type, distance)` plus an index, held in `MapScreen`, with both cards' Prev/Next routed to it while the card is inspect-opened. The marker side needs `MarkerPrevNext` to take callbacks rather than reading the ViewModel directly (the track side already takes them).
- **A cross-type step keeps the one card and changes its content.** The selected-item slot stays on screen and mounted; what changes is which panel it renders, followed by a resize to the new content's measured size using the same measurement the drawers already use when they open from a list. That means one selected-item surface with a content switch rather than two surfaces whose close and open animations play in sequence, and it holds **in both orientations**. "Resize to fit" is per orientation and means what a list open does there: portrait has a measured height to animate to, while landscape's panel is the fixed full-height column for both contents, so the content swap is the whole treatment — the same card the list would give you, not a second layout for the mode.
- **A step keeps its predecessor on screen until the successor is ready, and the slow direction is track→marker.** The canonical open is asynchronous, so *every* cross-type step passes through a window where no card has landed yet — but the marker open is the long one: `animateTo` for the pin, the settle delay behind it, then a background `whereAmI` before the drawer opens, where a track open waits only on its own detail load. The slot must hold the outgoing content through the whole of that window rather than emptying, or the swap blinks with the very close-and-reopen the single slot exists to remove.
- **The predecessor's close is deferred, and only for the mode's own card.** The openers' R1 close is skipped while a step is in flight and the landing effect closes the predecessor once the successor is on screen, in that same frame, so the slot's visibility OR never goes false. A predecessor the mode did not open closes at the step exactly as it always has — a track card's close restores the frame it was opened on, and deferring that restore to the landing would run it after the successor's own camera and yank the frame the open just set. The two provenance markers tell the halves apart: the marker card's `DrawerSource.INSPECT`, the track card's ladder.
- **A landing is the successor's own provenance, never "a card is open".** The held predecessor is still on screen at the step, and a same-type step's predecessor is a card of the *same* kind still showing the *previous* id — so the arrival test is the id this open is flying towards: the Viewing marker card on that id, the track drawer open on that id. Read any looser it fires at the step itself, spends the in-flight mark, disarms the mode early and then takes the successor's real arrival for the user having closed the card. One value carries both halves — the successor and the predecessor held for it — so "an open is in flight" has a single owner and no way to be left stuck true.
- **The held window is inert, not re-armable.** While an open is in flight the predecessor is on screen with live controls, and a step taken then would rewrite the navigate target, cancel the running open and leave the first card never landing: so the two walk buttons grey out (the marker card's through the same `InspectWalk`, the track card's through the held flag on its bundle), Back is swallowed rather than allowed to close the card out from under the landing successor, and the step carries its own guard — nothing may step while an open is in flight. The predecessor's own Delete and Edit stand down with them, because a delete-advance or a wizard entry taken in that window interleaves with the very open about to land on this slot — of the two options that is the one leaving the fewer reachable interleavings — and the stand-down rides the same `InspectWalk` the card is already handed.
- **A step that dies hands the cursor back, and an open that lands nothing lets go.** The cursor advances before the opener is called and is kept for the whole of that open, so an abandoned step puts it back on the slot the card still on screen shows rather than leaving that card's pills describing a successor that never arrived; the marker-delete advance re-seats it on the advanced neighbour, or drops it where the frozen ladder holds no such slot and falls back to the map world exactly as the undo path does. The abandonment itself is guarded on the in-flight open rather than on the world an open walks — an armed tap's open walks the map world and can land nothing just as easily — and the marker effect's tail runs on every exit of that effect, the null-`mapView` one included, so no hand-off can be left standing with the card's Back swallowed and the centre held. An inspect-sourced card that finds no cursor at all — disarmed while its open was still in flight — renders both pills at their end rather than enabled and dead, the same never-dead intent the undo fallback answers.
- **One opener, parameterised by its walk world.** There is a single selected-item opener that takes the world to walk — the frozen ladder from a pick, or the list world from anywhere else — rather than a second opener named after the list. Nothing inside it may reach for the list once a ladder has been handed over; that is the whole point of the cursor, and the parameter name has to say so.
- **The ladder carries the world it was ranked from, as a resolver.** The cursor holds a lookup over the map-filtered markers — the collection the ranking was built from, read live — and the marker opener resolves a step's id through it instead of against the list world. Handed the world its walk was ranked from and nothing else, a step can only die on an id that world has itself lost; resolved against the list world, an id the map filter keeps but a narrower list filter drops misses, `abandonInspectOpen` fires and the step is spent with nothing on screen. A resolver rather than the entity: a copied entity answers with the item as it stood when the ladder froze, so an edit shows a stale card and a delete resurrects one. The line half needs no counterpart — the ranking and the opener both load through the very same `loadTrackDetailCached`. A tap that lands on a marker while armed enters on the world the tap itself came from: with a ladder frozen the tap seats the cursor in it, and before any pick there is none to seat, so the walk is then that same map-filtered collection — never the list world, which may have filtered the tapped marker out and would seat the card on whichever marker its world happened to hold first.
- **The pick ends the armed half, and the card then holds the centre and the capture.** The stand-down *is* the landing: an open that lands no card leaves the mode armed, so a failed open is no exit. The capture taken at arming is not spent at the pick — it is retained until the card closes, which is the mode's single exit (§6) — so the frame the pick's camera just set stands for as long as the card does. The two follow gates — `notifyUserInteraction`'s resume timer and `setDrawerOpen(false)`'s spring-back — are keyed on **the card being on screen**, not on the armed flag, and the card's own pre-navigation restore stays stood down behind the ladder.
- **Two provenance markers tell a drawer which world it is in**: `DrawerSource.INSPECT` for the marker drawer, whose `scopeClosed` answers on the map world (a map-filter change closes the walk, as `MAP` does) and whose `isClampedSource` includes it; and, for the track drawer, an `inspectLadder: List<String>?` (null when opened anywhere else) that decides whether `trackListIds`/`currentTrackIndex` read the ladder or the list world, keeping a list-opened track walking the list even while armed.

## 6. Feed coupling, chrome and configuration

- **Arming** calls `freezeFollow()` (suppress + cancel the resume timer), so `syncCenterFromBoat` no-ops for the whole sweep: the user owns the centre, the marker answers only the map, and the follow effects stand down through their own `autoFollowSuppressed` guard. Demo needs nothing here — no fix drives the centre.
- **Two paths must be gated by the mode's hold on the centre** — armed, **or** an inspect card on screen — or the freeze is silently reverted: `notifyUserInteraction()` re-arms the resume timer on every pan, and `setDrawerOpen(false)` snaps back with `recenterNow()` whenever follow is suppressed, which would yank the anchor the moment an inspect card closes. Keyed on the card and not on `armed`, because the pick disarms the mode before its card is ever closed: the close then hands the centre back on the ordinary delay, never in that frame.
- **The capture is retained until the mode's single exit.** A pick keeps what arming captured; the exit applies it, once, and only when neither half of the mode is left — no inspect card standing and the armed flag down (`inspectLastExit`). A toggle with a card up therefore stands the armed half down and leaves the close to apply the capture, so the two paths cannot both restore, and an abandonment applies nothing because the mode is still armed with its card up.
- **The wizard's freeze wins.** Entering the wizard disarms the mode and *then* freezes follow: a disarm from a following map clears the suppression to recentre, and taken in the other order that clear would cancel the wizard's own freeze and let the boat retake the centre mid-wizard.
- **The RecenterButton** keeps its existing rule (`gpsMode && autoFollowSuppressed`) as the manual escape hatch; tapping it hands the centre back to the boat with the mode still armed, and the sweep continues from the new anchor.
- **Exit, GPS mode** — arming captures the follow state (the suppression flag plus whether a resume timer was live) and the exit applies it: a map already panned keeps its position and its delay-return **starts again from that moment** (a full `recenterDelaySeconds`, never the remaining time of the timer the mode cancelled, since a deadline left running underneath the mode would snap the boat back the instant it is disarmed), while a following map re-pins in the same frame. A map the user moved after the card opened takes the delay-return instead, whatever was captured (`inspectExitRePins`).
- **Exit, demo mode** — arming captures the centre and the exit puts it back, because nothing else can: the demo position is fed *from* the centre, so a swept map has carried the boat across it. A map the user moved after the card opened is left where they put it, the same guard the GPS half reads. Zoom is not restored, mirroring GPS, where a recentre also leaves the user's zoom alone.
- **Chrome follow-through** — the insertion moves the lock square one slot right, so the locked-screen mirror's offset `TOP_TOGGLE_GUTTER + (TOP_TOGGLE_SQUARE + TOP_TOGGLE_GUTTER) * 3` must follow it; better to derive the slot from the row order than repeat the literal.

## 7. Values and keys

| Key (`maro.properties`) | Meaning | Default |
|---|---|---|
| `ui.map.inspect.dwell.ms` | Post-lift quiet time — how long the map must stand still, with no user activity and no panel open, after a genuine finger lift before the highlighted item is picked | `666` |

The dwell key gets its own `AppConfig` accessor with its own clamp in the parse block beside the key's comment. The 🕵🏽 glyph is not a key: it follows the row's hard-coded glyphs. The radius trio, the movement gate and the hysteresis margin are gone with the ring, the gate and the stickiness (§2, §3, §5).

## 8. Verification

- **Unit tests** — ranking order and tie-break, the true closest winning on every re-rank with no stickiness to the previous winner, clear-on-empty followed by the resume when a candidate re-enters the viewport, bbox overlap for a point and for a cached line (a line whose box overlaps while no vertex is on screen), conflated ticks each publishing a result with no cancellation of the scan in flight, ladder ordering against a frozen anchor, the trigger clock's own pipeline — an activity bump, a candidate change and **a lift** each restarting the wait, and a panel suspending it with a fresh start on its close — and, beside them, the landing rule (a successor lands on its own id, never on the predecessor still on screen or on the other kind's card), the held-card decision (the mode's own other-kind card is the one held, and a card the mode did not open never is), the step's own resolution (a ladder id resolves in the world the ranking was built from, and the resolver answers with that world as it stands rather than as it stood) and the exit rule (the capture landing only when no inspect card and no armed half are left, and the re-pin decision against a capture already panned at arming and against a map the user moved after the card opened).
- **Build and chrome** — scoped run for the touched `ui.map` + `config` packages, `apk-build.bat` green; the six-square row fits the narrowest supported portrait width with the conditional recenter present, the locked-screen mirror still lands on the lock square, and 🕵🏽 renders as an emoji at the shared 22 sp toggle size.
- **Lift, quiet and re-arm** — a lift followed by a fling picks only once the map is quiet; a resting finger picks nothing however long the map stands still; a tap that never moved the map commits the highlighted item after the same wait — the lift is a field of the clock's own key, so that tap is a key change like any other and the seed's wait, which has no lift behind it, is spent without picking; arming with a candidate under the anchor opens nothing until a finger lifts (the seed paints the gold but starts no clock); and a re-armed session can pick the item the previous one picked, while the first session's own camera move cannot re-fire it.
